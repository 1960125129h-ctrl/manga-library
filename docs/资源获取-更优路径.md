# 资源获取链路：现状诊断与更优路径（实测版）

> 2026-10-22 实测。所有数字都来自本机真跑，不是估算。

## 一、现状：禁漫这条线有 6 个串联的失败点

当前 `run-albums.mjs` 下 1 话要依次跨过：

1. Chrome 带 9333 调试端口启动（且必须 Edge 之外、独立 profile）
2. 过 Cloudflare（TLS/JA3 指纹，node/curl 过不去 → 必须真实浏览器）
3. 点「免等待、點我直接下載」，再关掉弹出的广告页
4. 取会话级验证码 → EasyOCR 7 变体投票 → 串行提交（同一时刻只能有 1 个下载在途）
5. 等网站把整话打成 zip 落到 Downloads → 按 `<id>.zip` 收包
6. tar 解压 → 拷进目录 → 切页拼合 → 删包

实测成本：**单话 6.9~8.9 秒**，整本 15~21 秒；验证码答错就整轮重来；进程一断，zip 收包状态全丢。

## 二、关键发现：图片这一层根本没有 Cloudflare

实测（curl_cffi，impersonate=chrome，直连，无代理）：

| 请求 | 结果 |
|---|---|
| `https://cdn-msp.jmapinodeudzn.net/media/photos/1452133/00001.webp` | **200 / 101086 B** |
| 1452133 第 1~25 张（10 并发） | 1~15 全 200（2.75 MB / 6.5 s），16 起 502/404 |
| 1452134 第 1~25 张 | 1~22 全 200 |
| `https://18comic.vip/`（网页端） | 直连超时（被墙） |
| `https://www.cdnhjk.net/setting`（APP API） | **403 Cloudflare Managed Challenge**（cf-mitigated: challenge） |

结论：
- **网页端 + APP API 层挂 CF**（高频请求后从 200 升级成 challenge），这层绕不过去。
- **图片 CDN 不挂 CF**，URL 是定宽序号：`https://cdn-msp*.jmapinodeudzn.net/media/photos/<photo_id>/00001.webp`
- 页数越界的信号是 **502/503/404**（不是 403），所以「试到非 200 为止」就能自动得到页数，
  **不需要任何 CF 请求就能确定一话有多少页**。

## 三、三条更优路径（按落地成本排序）

### 路径 A（已实现，零风险，立刻可用）：把 zip 链路换成图片直取

`_scripts\jm\jm-img.py` + `run-albums.mjs --img`

    node _scripts\jm\run-albums.mjs JM1452133 --img
    node _scripts\jm\run-albums.mjs JM1452133 --img --img-workers=16 --from=1 --to=10

两种用法：
- 走 `run-albums --img`：浏览器仍负责**过 CF + 拿书名 + 拿章节表**（老逻辑不变），拿到之后不再点免等待、不再 OCR、不再收 zip，直接把 photo_id 列表交给 `jm-img.py` 并发拉图。
- 直接跑 `jm-img.py`：只要已知 photo_id，**连浏览器都不用开**。

    python _scripts\jm\jm-img.py 1452133 1452134 1452135 --book "书名" --workers 12

实测（本机，直连，无代理）：

| 方式 | 单话耗时 | 依赖 |
|---|---|---|
| 老 zip 链路 | **6.9~8.9 s/话**（串行） | Chrome + Clash + 验证码 OCR + 广告页 |
| 图片直取（jm-img.py） | **1.7 / 2.9 / 4.0 s**（15/22/16 张） | 只要 HTTP，无浏览器、无验证码 |
| 3 话合计 | 老 21~27 s → 新 **9.7 s** | |

jm-img.py 已带的能力：图片域名池轮换、越界判定、扩展名探测（webp/jpg/png/gif）、
断点续传（目录里已有连续编号就从下一张接着下）、`--stitch` 可选拼合、`__JSON__` 结果清单。

注意：直取的图**已经是解码后的完整页**（`stitch-pages.py --dry` 实测「合并 0 处，页高 1005/1365/1365，无异常页」），
所以 `--img` 模式**故意跳过 stitch**，避免把已经完整的图再转码一遍（会掉画质）。

### 路径 B（已实现，能过 CF 时最快）：jmcomic 官方 API 直取

`_scripts\jm\jmcomic_dl.py` + `jm-fast.mjs`

    node _scripts\jm\jm-fast.mjs JM1452133
    node _scripts\jm\jm-fast.mjs 1452133 --from 1 --to 20 --image-workers 16

用的是社区维护的 `jmcomic`（Python，pip 包，本机已装 2.7.9），能力覆盖：
APP 接口加解密、curl_cffi TLS 指纹、域名池自动切换、**图片乱序解码**、
章节级 + 图片级双并发、已存在图片自动跳过、tags/作者/页数/发布日期等元数据。

实测：`--dry` 一次把整本 163 话 / 1237 页的章节表全拿到；第 3~6 话（41 张图）下载 **9.5 s** 落地。
但它初始化要打 `/setting`，**API 层被 CF 挑战时直接 403**（本次实测就是如此），
所以它属于「有干净出口 / 代理可用时」的最优解，不适合当唯一路径。

三者定位：
- 平时：`run-albums --img`（路径 A），最稳。
- 有代理或 API 没被挑战：`jm-fast`（路径 B），顺带把元数据（tags/作者）一次灌进 library.json。
- API 被挑战又不想开浏览器：直接喂 photo_id 跑 `jm-img.py`。

## 五、踩坑记录（本轮新增）

1. 禁漫 APP API 域名（www.cdnhjk.net 等）**直连会被 CF 升级成 Managed Challenge**（403，cf-mitigated: challenge）。
   出现这个就别再重试同一个域名，换出口 IP 或改走浏览器。
2. 图片 CDN 的越界信号是 **502/503**，不是 404。把 502 当「域名坏了」去换域名重试，
   会把一话的耗时从 2 秒拖到 20 秒。
3. jmcomic 的 decide_image_save_dir 走的是 photo.from_album；单话模式下 save_path 不一定可靠，
   **自己按 base_dir/书名/第NN話 重算目录**比读内部状态稳。
4. jmcomic 的 check_photo 在 before_photo **之前**执行 —— 想在 photo 层做区间过滤是没用的，
   会先把每一话的 /chapter 请求全打出去（实测 163 话打了 163 次）。区间过滤要改在 album.episode_list 上做。
5. Windows 下 PowerShell `*>` 重定向写的是 UTF-16，Node 的 readFile(utf8) 会读出夹空格的乱码；
   跨进程传中文统一加 `PYTHONIOENCODING=utf-8`。

## 七、第一轮实测暴露的三个问题（2026-10-22 修复）

### 1. 图片乱序（页码错乱、每张偏移不同）—— 我的实现漏洞
禁漫每张图按 `scramble_id` 做行分段重排，**直接从 CDN GET 到的是打乱版**。
`jm-img.py` 第一版直接落盘，漏了解码；`jmcomic_dl.py` 走官方 API 自带解码，所以那本尼古喵喵是好的、单话本是乱的。

修法：
```python
scramble_id = client.get_scramble_id(photo_id)          # 一次 API 请求
num = JmImageTool.get_num_by_url(scramble_id, img_url)  # 分段数，逐页不同
JmImageTool.decode_and_save(num, JmImageTool.open_image(data), dst)
```
拿不到 `scramble_id` 就整话跳过，**绝不下乱序图**。
每话落盘后写 `.jm-decoded` 标记（含 scramble 与张数），下次自动跳过；`--force` 才重下。

验证：同一话分别用 jm-img 与 jmcomic 各下一遍，**27/27 张 md5 完全一致**。
书库里那本《小小只萝莉妈妈…第8話》27 张已按此重下，并与官方解码版逐张比对通过。

### 2. 需要登录吗 —— 不需要
日志实测 `[页面] 登录状态: failed` 仍然 27 张 4.4 秒下完。
- 图片 CDN：无账号、无 CF
- 接口/专辑页：也不需要账号
- 例外：站点对部分作品做了登录可见，API 会返回「该漫画只对登录用户可见」，这时才需要 cookie/登录态

界面文案已改：「浏览器（仅老方式需要；不登录也能下，遇到隐藏内容再登录）」。

### 3. 「还是压缩包解压」—— 那一次不是直取
日志里 15:22 那轮是直取模式但**被取消**（退出码 null），15:24–15:25 那轮才是成功的直取，日志无收包/解压。
重建书库时刷新的「图标」是 thumbs 生成缩略图，与下载无关。

### 4. 顺带修掉的 ID 解析 bug
`https://18comic.vip/album/1484921/` 用 `\d+` 抓数字会把域名里的 **18** 也拼进来 → 变成 `JM181484921`。
现在链接优先按 `/album|photo/(\d+)` 取，纯数字/ JM 号才走拼接。

### 5. 浏览器依赖重排
直取模式现在：**先走接口（不开浏览器）**，接口被 Cloudflare 拦（退出码非 0）才回退「浏览器取章节表 + 图床直取」。
App 里实测日志：`[1] 走禁漫接口直取（不开浏览器）` → 完成后直接收尾，全程没有启动 Chrome。

## 八、重建改成增量（2026-10-22）

**问题**：每次下载完都跑全量重建 —— 要遍历 1160 本 / 12 万个文件，20~30 秒。

**现状**：`build-library.mjs` 其实早就有 `--only "漫画/书名"`（`incrementalScan`，只扫指定书，其余从 `_manifest.json` 沿用），
但三条下载链路都没传它。

**改动**：
| 位置 | 改动 |
|---|---|
| `jm-fast.mjs` | 收尾从「全量」改为 `--only` + 本次实际落盘的目录（取自 jm-img/jmcomic 返回的 dir，含简繁匹配后的真名） |
| `run-albums.mjs` | 同上；直取分支解析 jm-img 的 `__JSON__` 拿真实目录；老 zip 分支按 title 记 |
| `jm-auto.mjs` | 子脚本已增量重建 → 跳过；失败或导入过手动包 → 全量兜底 |
| `main.js` | 退出码 0 时**不再全量重建**（子脚本已做），非 0 才兜底；等待时间 3s → 1.5s |

**实测**：单独跑一次增量重建 **7.3 秒**（全量约 25 秒）；一条龙的「下载 1 话 + 增量重建」**15.2 秒**。

**为什么不能更低了**：`书库.html` 是单文件、内联全书数据（3.2 MB），增量也必须整体重写；
另外识别（作品/角色匹配、作者清洗、分级）要在全部 1160 本上跑一遍，这部分是内存计算。

**顺带清掉一处脏数据**：同一本书在库里出现了简体/繁体两个目录（第一次直取用界面传的简体名建目录，后来 jmcomic 用 API 返回的繁体名又建了一个）。
已把简体那份移到 `_backup\dup-*`，并清掉 library.json 里的孤儿键。

## 九、NH（nhentai）提速（2026-10-22）

**根因**：`fetch-book.mjs` 的通用下载器并发写死默认 4，nhentai 没单独覆盖。

**实测**（同一本 20 张 / 5.7MB，走代理）：

| 并发 | 耗时 | 每张 |
|---|---|---|
| **4（改前默认）** | **12.5 s** | 624 ms |
| 8 | 5.7 s | 284 ms |
| 12 | 4.2 s | 211 ms |
| 16 / 20 | 3.6 / 3.3 s | 182 / 167 ms |

全程 200，**没触发 429**。瓶颈是并发度，不是带宽。

**改动**：
| 文件 | 改动 |
|---|---|
| `sites/fetch-book.mjs` | 并发改为按站点取：`adapter.jobs` 优先，否则默认 8；上限 12 → 20；`--jobs` 仍可覆盖 |
| `sites/nhentai.mjs` | `export const jobs = 12`；图片 URL 从固定 `i1` 改成按页号在 `i1~i4` 轮换 |
| `sites/ehentai.mjs` | `export const jobs = 4`（509 配额，提并发只会更快撞配额） |
| `sites/pixiv.mjs` | `export const jobs = 2`（i.pximg.net 会 429） |

**验证**：`--probe` 枚举 55 页，URL 形如 i1/i2/i3/i4 交替，符合预期。

**注意两点**：
1. nhentai 的图片 CDN **直连全部超时**（和禁漫图床不同，禁漫图床可直连），只能走代理，所以天花板是你的代理带宽。
2. `fetch-book.mjs` 的"只枚举"参数是 `--probe`，**不是 `--dry`**（`--dry` 会被忽略并真下载）。

其它站没动：pixiv 卡在 429 退避、EH 卡在图片配额、komiic 卡在每日配额、漫画柜/包子卡在 CF —— 这些瓶颈都不在并发，提并发不会更快。

## 十、EH 提速与画质档位（2026-10-22）

### 先说最重要的发现：我们一直在下缩水图

EH 的 `/s/` 页面上有两条地址：
- `<img id="img">` = **1280×1920 降级档**（0.05~0.19 MB）—— 我们一直在用它
- `Download original` = `/fullimg/...` = **原图**（那本是 4672×7008 / 12~15 MB，但不是通用值，见下方补正）

像素差 **13 倍**。EH 用户页原话：`Due to a high request rate, your IP is currently restricted to lower-resolution images.`
这是按 **IP** 算的（不是账号配额），高频访问就被摁在降级档。

抽查库里 424 本 EH 来源的书，图片全是 1280×1920。

### 提速：三处

| 环节 | 改前 | 改后 | 实测 |
|---|---|---|---|
| 翻页拿 `/s/` 链接 | 完全串行 | 并行 4 页一批 | 4 页 0.8s（全 200） |
| 解析 `/s/` 页 | 并发 4 | 并发 8（`EH_JOBS` 可调，上限 10） | 16 页 4.4s → 1.8s |
| 图片下载 | 并发 4 | 并发 8（`export const jobs = 8`） | 收益最小，受配额/带宽约束 |

**整本实测**：53 页的画廊，`images()` 从约 12.5 秒降到 **4.8 秒**。

1999 张的大图包（降级档）估算：翻页 20s + 解析 211s + 下载 87s ≈ **5 分钟**（改前 11 分钟以上）。
切到原图则相反：单张 12MB、4~24 秒，一本 1999 张约 **30 分钟 / 20+ GB**。

### 画质档位：放进设置了

**设置 → 高级 → 下载 → E-Hentai 画质档位**
- 降级档（站点压缩版，快，**默认**）
- 原图（按站点标注的原始尺寸，单张几 MB~十几 MB，每张都不同，很慢）

存在 `_scripts/sites/download-prefs.json`，适配器直接读；环境变量 `EH_QUALITY=original` 可临时覆盖。
只影响 EH，对 nhentai / 禁漫 / 其它站无影响。

### 一个坑

EH 图床节点端口很杂（443 / 4443 / 8443 / 45123 / 62000），个别节点（实测 `*.hath.network:62000`）代理连不上，会偶发 SSL 断连。现有的 3 次重试能兜住，但失败率会比只有一个域名时高。

### 补正：原图尺寸不是固定值

初版我把一本的数据（4672×7008）当成通用尺寸，不对。抽查四本：

| 书 | 原图尺寸 | 体积 |
|---|---|---|
| 纸悦 | 4672×7008 | 13.99 MB |
| 清水凪 忍野忍 | 5295×7944 / 5419×8129 | 1.63 / 1.72 MB |
| 清水凪 五更琉璃 | 4672×7008 | 4.38 MB |
| 清水凪 艾莉丝2 | 4108×6163 / 4064×6096 | 3.62 / 3.97 MB |

尺寸和体积跟着上传者的原始文件走，同一本里每页都可能不同。
页面上的标注才是真值：`Download original 4672 x 7008 13.99 MiB`。

代码里没有写死任何尺寸，`origOf()` 只抓 `/fullimg/` 那个链接，抓不到就退回降级档。

### 原图 → 降级档 回退

实测发现**降级档本身也会下载失败**（图床节点抽风）。所以原图模式下每页都带一个降级档备用：
主地址 3 次重试还失败 → 自动改用备用档兜住这一页，不让整页丢掉。
`fetch-book.mjs` 的下载器加了通用的 `alts` 回退（其它适配器以后也能用）。

## 十一、EH 下载失败的真相：代理不放行高端口（2026-10-22）

### 症状
145 页的画廊只下到 99 张，**46 张失败**，整本拖到 3 分多钟。

### 定位过程
1. 失败原因全是 **ECONNRESET**，不是 403/509（不是配额、不是封禁）
2. 并发 8 和并发 4 的失败率**完全一样**（30%），不是并发问题
3. 逐张打主机端口，规律出来了：

| 端口区间 | 走代理 | 直连 |
|---|---|---|
| 443 / 2333 / 2683 / 4443 / 4496 / 8443 / 8909 | **全通** | 个别超时 |
| 22334 / 32768 / 43744 / 45122 / 45123 / 45260 / 51145 / 62000 | **全 ECONNRESET** | **全通** |

**代理只放行低端口**，EH 的 H@H 图床有一批节点在高端口上，走代理必挂。重解析 /s/ 页换不到别的节点（节点是固定的）。

### 为什么不能直接「同进程内直连」
Node 24 的 NODE_USE_ENV_PROXY=1 连 https.request 一起接管了：
同一条 62000 端口的 URL，带代理环境 ECONNRESET，去掉就 200。所以同一个进程里没法只让某一张图直连。

### 解法：失败时调系统 curl 直连
curl.exe --noproxy '*' 不认那个环境变量，实测 62000 端口 200 / 137KB / 0.79s。
下载顺序变成三层：**代理 → curl 直连 → 适配器备用档**。

原:代理 --失败--> 重试3次 --失败--> 丢页（还要拖 3 次退避）
新:代理 --失败--> curl 直连（一般就通了）--失败--> 原图/降级档互换 --失败--> 丢页

### 效果（同一本，取前 24 张）

| 方案 | 成功 | 体积 | 耗时 |
|---|---|---|---|
| 只用代理 + 原图兜底 | 19/24 | 62.8 MB | 49 s |
| **代理 + curl 直连** | **24/24** | **1.8 MB** | **4.5 s** |

24 张里有 9 张靠 curl 直连救回来，**没有一张需要退到原图**，所以体积没膨胀。

### 顺带：日志重复的根因
preload.js 的 onDownload 把去重标记挂在回调函数对象上，而下载弹窗**每次打开都传一个新的匿名函数**，
于是监听器越堆越多，开两次就每条日志显示两遍。已改成按「槽位」替换：onDownload(cb, slot)。
